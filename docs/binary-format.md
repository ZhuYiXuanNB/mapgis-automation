## 一、当时测到、后来印证无误的部分

| 文件 | magic (0–7) | 文件标识 (8–11) |
|---|---|---|
| `.WT` 点 | `WMAP\`D22` | 1 |
| `.WL` 线 | `WMAP\`D21` | 0 |
| `.WP` 区 | `WMAP\`D23` | 2 |

- 索引区起始位置在第 12–15 字节（int32），实测 **657**（要读，不能写死）
- 第 264 字节（int32）= **图元数 + 1**
- 点记录 **93 B**、首块为空：`点数 = coord_volumn / 93 - 1`
- 线索引 **57 B**、首条为空：`线数 = line_volumn / 57 - 1`
- 线文件坐标区开头有 **2 字节前缀**，之后每 16 字节一对 double
- 每 39 字节一个字段描述符（0 基从 **348** 起，349 是 1 基写法）

实测校验（当时）：

| 文件 | 大小 | `coord_volumn` | 反算点数 | 实际 |
|---|---|---|---|---|
| 控制点.WT | 298 820 | 206 553 | 2 220 | 2 220 ✓ |
| 重复样.WT | 7 236 | 4 185 | 44 | 44 ✓ |
| 500m小格线.WL | 8 397 | 1 378 | 43 条 | 43 ✓ |

## 二、手工拼装为什么会失败（本仓库最有价值的一次排查）

当时用上述结构把 `.WT`/`.WL` 拼成"读得回、点数正确"的文件，MAPGIS **一律拒绝加载**（图面空白、无报错）。
逐字节对比生成文件与可正常显示的模板，**前 817 字节只差 20 个字节**，全是被清空的三个附属段指针：

```
+20/+24   属性段      4703 / 607
+40/+44   附加表 A    6366 / 55
+60/+64   附加表 B    6813 / 1408
```

也就是说：**失败的根因是缺段，不是"MAPGIS 不接受手工文件"。**

## 三、结论修正（重要）

| 旧结论（本文早期版本） | 现在（2026-11 下旬） |
|---|---|
| "不要试图手工拼装，MAPGIS 一律拒绝" | **补齐段即可**：点文件 5 段（记录/文本池/属性/标注框/标志）、线文件 8 段（线/坐标/属性/结点/55B/元数据/框表/标志），并从真实文件克隆 657 B 头 → 可被解析、可被 **MAPGIS 正常加载并显示**。已实测验收：见 [verification.md](verification.md)（2026-11-26，SECTION + 编辑子系统）。 |
| "注记文字在属性记录 +20 处" | 注记文字存在**文本池**：点记录 `@1 = 文字字节数`、`@3 = 池内偏移`，池首 1602 B 是样式前缀，之后才是拼接的 GBK 文字。 |
| "字段定义区从 349 开始" | 0 基为 **348**。 |

## 四、仍然成立的两条经验

1. **保守做法最优**：能克隆就克隆——头 657 B、附属段（`55 B`、`392 B` 元数据）都直接从真实文件抄，
   只替换记录/坐标/属性/文本。
2. **改完文件必须让 MAPGIS 重读**：移除图层 → 重新添加项目 → 复位窗口。
   否则看到的是缓存，误以为"没生效"（这条在文件级与界面级都适用）。
